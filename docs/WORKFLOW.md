# Процес каруселей — проєкт v0.2

Останнє уточнення власника 2026-10-18: прибрати окремого рецензента й автоматичний перегляд результатів після генерації. Це замінює попередній запропонований етап QA.

Стиль НЕ затверджено. Claude, хмарний генератор, автоматичні запуски й віддалений канал outputs ще не підключені.

## Спільні референси

references/CAROUSELS.md — єдине місце, куди власник додає скриншоти. Один REF-XXX розділ містить одну карусель; порядок image links визначає порядок слайдів.

У brief записувати конкретні REF-ID, commit файла й потрібні URL/порядок. Візуальні дані мають реально відкриватися у середовищі виконавця: Markdown або синхронізація тексту з GitHub самі по собі не передають картинки генератору. За відсутності потрібних пікселів — точний блокер. На комп'ютер власника нічого не завантажувати.

Після першого розбору записати корисний витяг у brief. Наступний агент читає призначений витяг і потрібні слайди; не аналізує всю колекцію щоразу. Повторне прикріплення в кожному чаті не є штатним процесом.

## Ролі

- Координатор: теми, ID, пакет, залежності, обсяг, прогрес і передача.
- Claude: brief.md і точний copy.json — hook, послідовність слайдів, caption, продуктовий фінал, visual briefs та джерела для змістовних тверджень.
- Codex/ChatGPT: ціла карусель за конкретними текстами та пробною/затвердженою версією оформлення; збереження prompts/outputs.
- Власник: перегляд готових слайдів, вибір стилю, правки й прийняття.

Окремого рецензента немає. Не запускати додаткових агентів, повторних візуальних оглядів, OCR чи платних викликів для оцінювання готових слайдів. Не називати результати перевіреними: agent_visual_review=not_performed. Для фітнес-контенту коректні джерела/техніка потрібні при підготовці тексту і промпту; це не окремий післягенераційний review.

## Порядок роботи

1. Власник додає референси в один файл.
2. Координатор готує одну карусель із темою, аудиторією, REF-ID й продуктовою прив'язкою.
3. Claude пише тексти та короткі visual briefs, зберігає версію.
4. Візуальний агент бере зафіксований текст і доступні референси; генерує окремі слайди як одну узгоджену серію.
5. Зберігає фактичні файли та журнал спроб; передає власнику без агентського візуального перегляду.
6. Власник дає фідбек. Корекції стосуються лише вказаних слайдів.

Поки стиль досліджується, виконувати лише замовлені проби. Після вибору стилю й одного завершеного пілоту пропонується стартовий пакет із 3 каруселей; це пропозиція, не поточний запуск.

## Одиниця роботи й передача

ID на кшталт LW-CAR-0001; одна папка carousels/LW-CAR-0001/ і одна робоча гілка на карусель.
Файли: brief.md, copy.json, manifest.json, prompts/, handoff.md; результати зберігаються у фактично вибраному віддаленому сховищі.

Один візуальний агент веде цілу карусель. Різні каруселі згодом можна робити паралельно. Не ділити її слайди між незалежними виконавцями без спільного master/reference.

Маніфест каруселі редагує призначений виконавець; глобальний progress оновлює координатор. Це процедурне правило, не встановлений автоматичний lock. Після інтеграції тексту передавати конкретний commit/content_version. Візуальний агент не переписує текст самостійно.

## Мінімальний журнал

Для слайда: slide_id, content_version, style_version, prompt, reference IDs, generation_id, attempt_history, result URL/path і реальний статус збереження. Підготовка prompt не рахується запуском.

Прогрес зберігати після кожного слайда, handoff — після каруселі або переривання. Не запускати окремі скрипти аудиту, перевірки анатомії чи хешування результатів за замовчуванням. Достатньо записати, який файл фактично повернув генератор і чи успішно завершилась передача у вибране сховище. Помилку збереження не маскувати.

Не прирівнювати файл до схвалення. user_review=pending до явного рішення власника. approved позначає лише точну прийняту версію. Непроведені перевірки позначати not_run/not_performed.

## Ліміти й відновлення

Перед запуском перечитати поточний manifest. Прийняті та вже згенеровані слайди не повторювати без запиту. Після переривання спочатку звірити журнал із фактичними outputs; статус in_progress сам по собі не означає, що результату немає.

Використовувати вбудований image_gen лише де він фактично доступний. Не переходити на платний API як запасний спосіб. На квоті зупиняти пакет й зберігати точний наступний крок. Без окремого завдання автоматичні корекції вимкнені.

Тимчасовий хмарний шлях не є постійним сховищем. Записувати реальний віддалений URL після успішної передачі. Нічого не клонувати й не завантажувати на пристрій власника.

## Фінальний слайд

Поєднує тему каруселі з реальною функцією Lightweight і конкретною наступною дією. Загальний Save your next... із доданою назвою бренду недостатній. Конкретний CTA/дизайн ще не затверджено.

## Наступний етап

Спочатку наповнити спільний файл референсів, опрацювати стиль і пройти одну карусель до віддалено збереженого результату. До цього не стверджувати, що вся автоматизація вже працює.

## Продуктові матеріали та макети телефону

references/APP-SCREENS.md — друге спільне джерело: оригінальні екрани Lightweight, окремо від прикладів каруселей. Один APP-ID відповідає одному стану/мові/темі. Власнику достатньо додати назву й чистий скриншот; метадані допоможе доповнити координатор.

У brief зазначити потрібний APP-ID, commit та image URL. Для фіналу спочатку визначити реальну користь, потім вибрати відповідний екран. Наприклад, тема тренування може пов'язуватися із записом підходів, якщо такий екран фактично надано. Наявність скрина не підтверджує релізний статус функції.

Для макета «рука тримає телефон з нашим екраном» запропоновано два етапи: генерація сцени з придатною площиною дисплея та накладання оригінального UI окремим шаром із перспективою/маскою. Так можна зберігати справжній контент UI; генеративний перемальований екран не позначати точним. Цей модуль поки не реалізовано. Для читабельності обирати ракурс і розмір телефону відповідно до задуму; телефон не обов'язковий у кожній каруселі.

Файл поки містить лише порожні місця. Немає імпортованих екранів або готового mockup pipeline. Усе виконується віддалено, без завантаження на пристрій власника та без додаткового автоматичного QA.
