# Проєкт процесу — v0

Статус: proposed. Це документація, не запущена автоматизація.

## Що перевірено в попередньому проєкті
Прочитано AGENTS.md, docs/exercise-image-workflow.md і поточний початок docs/handoff.md у гілці work репозиторію lightweight-exercises-photo, станом на 2026-10-18.

Зберігаємо корисні механізми: стабільні ID, невеликі пакети, окремі реальні спроби, точні прийняті результати, окремі технічна/візуальна/користувацька оцінки, контрольні точки й відновлення. Старі ліміти пілоту, квадратний формат, прозорість, перелік вправ, політику Supabase і історичні дозволи сюди не переносимо.

## Етапи
1. Підготовка: палітра, продуктова довідка, теми, ролі, доступні референси.
2. Дослідження стилю: замовлені власником проби; style_status=exploring.
3. Після явного вибору стилю: одна повна пілотна карусель.
4. Перевірка пілоту: текст, анатомія/обладнання, оформлення та релевантний CTA.
5. Після дозволу на випуск: запропонований стартовий пакет — 3 каруселі. Перегляд після кожної каруселі; розмір наступного пакета визначати за результатами.

## Ролі й одиниця роботи
- Координатор: формує пакет, призначає ID і виконавця, веде зведення.
- Claude: готує brief та copy.json із текстами й джерелами.
- Візуальний агент Codex/ChatGPT: оформлює цілу карусель, зберігає сталість між її слайдами.
- Рецензент: робить один узгоджений прохід перевірки, повертає конкретні проблеми.
- Власник: задає напрям, затверджує стиль і результати.

Один візуальний виконавець веде одну карусель. Після пілоту можна паралелити різні каруселі. Не роздавати слайди однієї каруселі незалежним виконавцям без спільного master/reference.

Ці ролі не означають, що агенти зараз запущені або інтеграції вже підключені.

## Пакет і передача
Карусель має ID LW-CAR-0001. Її папка: carousels/LW-CAR-0001/.
- brief.md — тема, аудиторія, обіцянка, референси, продуктова прив'язка;
- copy.json — точний текст кожного слайда, visual_brief, CTA й джерела;
- manifest.json — версії, виконавець, статус, спроби та результати;
- prompts/ — фактичні промпти генерації;
- review.md — перевірки та фідбек;
- handoff.md — що виконано, блокер і наступна конкретна дія.

Маніфест однієї каруселі редагує один призначений виконавець. data/carousel-progress.json як зведення оновлює координатор після інтеграції. Це процедурне правило, не автоматично встановлений GitHub lock.

Виділяти одну гілку на карусель; перед передачею наступному етапу інтегрувати затверджений текст і зафіксувати commit. Зовнішня гілка не рахується збереженою в main. Не підміняти наявність PNG схваленням.

## Контракт текстів
У copy.json потрібні carousel_id, language, audience, content_version, product_feature, sources і slides.
Для кожного слайда: slide_id, role, headline, body, visual_brief; exercise_data — за потреби.
Фінальний слайд: проблема/наступний крок читача + конкретна реальна функція Lightweight + доречна дія.

Після передачі в генерацію текст зафіксовано на певному commit/content_version. Візуальний агент не переписує його самостійно. Правка тексту створює нову версію й перелік слайдів для оновлення.

## Генерація й історія
Перед запуском перевірити наявність вбудованого image_gen, читабельних референсів і потрібних даних. Не називати SDK або API-ключ доступом до вбудованого генератора. Платний API не є погодженим запасним способом; зміну провайдера узгоджувати окремо.

Перед кожною генерацією перечитати manifest. Не повторювати прийняте. Записати prompt, style_version, content_version, reference IDs, generation_id і факт запуску. Після відповіді одразу записати результат/помилку. Підготовлений prompt не є спробою.

На квоті/недоступному інструменті зупинити пакет та записати handoff. Не витрачати виклики на решту черги після відомого quota block. Після переривання спочатку звірити фактичні результати й журнал; in_progress не є доказом відсутності output.

Кількість автоматичних виправлень має бути задана в пакеті до запуску. Якщо не задана — повтори не запускати; позначити конкретну проблему. Явне доручення на корекцію дозволяє тільки вказані слайди.

## Перевірки й прийняття
Зберігати окремо:
- technical_check: not_run / passed / failed;
- content_review: not_run / passed / needs_fix;
- agent_visual_review: not_performed / passed / needs_fix;
- user_review: pending / approved / changes_requested;
- remote_backup: not_saved / saved_unverified / verified.

Технічні перевірки: файл відкривається, фактичні dimensions/формат, порядок слайдів, hash і відповідність manifest. Цільові розміри визначить майбутня специфікація стилю; не припускати 4:5 або 1080×1350 затвердженими.

Візуальна оцінка: один прохід у погодженому пакетом режимі; фактична перевірка анатомії, механіки обладнання, тексту/переповнення, єдності серії, CTA. Не запускати додаткових агентів лише для простих файлових перевірок. Непроведений перегляд так і позначати.

Агент не ставить user_review=approved. Прийнята версія має точний незмінний accepted asset/hash. Зміна стилю не запускає автоматичне перегенерування старих матеріалів.

## Зберігання й відновлення
На комп'ютер власника нічого не завантажувати. Майбутній медіаканал — віддалений GitHub/Release або інше явно вибране сховище; зараз канал передачі binary ще не налаштований.

Для фактичного збереження записати реальну URL/шлях, розмір, SHA256 та commit/release. Статус verified — лише після перевірки віддаленої копії. Тимчасовий шлях хмарного середовища не є постійним сховищем і не гарантується в новій сесії.

Звіти окремо показують: тексти готові, візуали згенеровані, збережено віддалено, потребують правки, прийнято власником, заблоковано. Лічильники — з manifests, не з пам'яті чату.

## Запуск
Спочатку проходимо одну карусель від brief до перевіреного віддаленого результату. Лише після цього можна стверджувати, що передача Claude → генератор працює. Розклад, автоматичний запуск і публікацію поки не налаштовано.
